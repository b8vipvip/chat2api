# Chat2API Web Chat Client v1

Status: first interactive browser client; not a complete ChatGPT 1:1 replacement.

## Entry points

- `GET /chat` serves the standalone chat UI.
- `/console` links to the chat client.
- `/assets/chat2api-image-drop-v1.js`, `/assets/chat2api-chat-client-v1.js` and `/assets/chat2api-chat-client-v1.css` are served with no-store headers.
- The HTML response applies a restrictive same-origin Content Security Policy and `X-Content-Type-Options: nosniff`.

## Authentication and API flow

1. The page checks the existing user session through `GET /api/user/me`.
2. It lists the signed-in user's own API Keys through `GET /api/user/keys`.
3. The user selects an enabled, non-expired Key with recoverable secret and `chat` scope.
4. The page fetches that Key's secret through the existing owner-checked `GET /api/user/keys/{key_id}/secret` endpoint.
5. The raw Key is held only in page memory and used as a Bearer token for the dedicated `POST /api/user/chat/completions` Mode 1 Web Chat ingress. The page revalidates the same user session before each chat request. The Key ID preference may be stored locally; the raw Key is never written to localStorage.
6. The Mode 1 ingress requires the signed-in user session, a same-origin browser request (Origin / Fetch Metadata), and the selected managed API Key; it rejects the administrator master key and verifies that the user owns the Key.
7. The Mode 1 adapter invokes the same internal Chat Completions request handler used by Mode 2. That shared handler retains the existing model policy, quota/wallet admission, Worker selection, RequestBroker, ChatRequestService and terminal/billing owners; Mode 1 does not call the OpenAI-compatible `/v1/chat/completions` route.
8. On bootstrap, the client reads owner-scoped server conversations through GET /api/user/chat/conversations, merges them with the account's legacy local cache, and uploads local-only conversations with revision 0. Conversation GET/PUT/DELETE requests are authorized only by the HttpOnly user session; a caller-supplied user ID is never accepted.
9. Conversation PUT uses an expected server revision and enforces same-origin browser request metadata plus a bounded request-body size before JSON parsing. Import and DELETE enforce the same origin boundary. Concurrent tabs/devices receive 409 with the latest row, merge message IDs and retry; transient network/5xx sync failures use capped exponential backoff, while permanent client errors are surfaced without blind retries. DELETE writes an owner-scoped tombstone so a stale device cannot silently resurrect a deleted conversation.
10. Stop requests use the same user-session cancel endpoint. If the request is still queued, the server signals the pending admission task and waits for its terminal projection; if already running, it serializes the cancel message behind the initial Worker dispatch. The browser aborts the generation POST only after this cancellation handshake returns.
11. In parallel, the browser opens a user-session native-content sidecar for the same request ID. The sidecar checks that the signed-in user owns the API Key recorded in Telemetry, then reads the same validated NativeContentStore snapshot and archived media records. It never dispatches a second generation.

The page sends the full ordered conversation using the Chat2API Web Chat request schema (`model`, `messages`, `stream`). The server's default full-history behavior preserves multi-turn context; no private `prompt_mode` field is required.

## Implemented in v1

- Responsive dark/light chat layout with desktop sidebar and mobile sidebar.
- User-session check and owner-scoped API Key selection.
- Online model list with user model-catalog fallback.
- New conversation, conversation list, server-side search across saved history (including conversations outside the 15-item local recent window), rename and delete. Search is owner-scoped, bounded and treats query text literally. Server persistence uses a private SQLite database with per-user ownership, optimistic revisions, conflict merging and deletion tombstones; browser localStorage remains a local cache and the one-time source for migration of older local conversations.
- Image attachments: PNG, JPEG, WebP and GIF; up to 4 combined attachments per message, 10 MiB per image and 20 MiB total per message. Document attachments support PDF, TXT, Markdown, CSV, JSON, RTF, DOCX, XLSX and PPTX; each document is limited to 20 MiB and uses the existing FileStore with purpose `assistants`. Images can be selected, pasted or dragged onto the composer; documents are selected through the dedicated file picker. Image drag/drop uses an isolated event adapter and funnels accepted File objects through the same MIME/size/key-owner validation as the picker. Images are uploaded through Chat2API's JSON `/v1/files` endpoint under the selected Key's `files` scope. The message uses the standard Chat Completions `image_url` content-part envelope, with a Chat2API-specific `file_...` reference in `image_url.url` to avoid storing/re-sending base64 bytes in browser history.
- Streaming Chat Completions, incremental text, stop generation and incomplete-stream warning when `[DONE]` is missing.
- W-04 request recovery: each turn carries a request ID, pending request/message identity is stored in account-scoped local history, and reconnects resume the same request without re-posting generation. The owner-scoped SQLite event journal persists delivery deltas and terminal markers; the browser replays from `Last-Event-ID`, while the recovery endpoint provides a final Telemetry/journal snapshot when available. Worker terminal outbox replay after Broker restart is reconciled conservatively and never triggers a second generation.
- Safe Markdown fallback with nested ordered/unordered lists, read-only task checkboxes and strikethrough, plus a Mode 1 native-content renderer for validated HTML layout, SVG charts, expanded MathML structures (including matrices and fenced expressions), archived images, generated files and clickable citation links restricted to public HTTPS destinations. Citation links open in a new tab with no referrer and no opener. The renderer builds DOM nodes from allowlisted tags, styles, SVG attributes and link targets; it never inserts captured HTML or executes scripts. The user-session sidecar streams revisions and finality for the same request ID.
- Copy message/code and export the current conversation to Markdown or versioned JSON (up to 5 MiB). JSON import is owner-scoped, validates every message, API Key and attachment reference, refuses to overwrite an existing conversation ID, and restores the conversation as a new revision. JSON exports preserve attachment IDs and metadata, not the underlying binary file bytes.
- Conversation history is persisted server-side per authenticated user and synchronized across devices. The localStorage copy is a bounded offline/cache fallback and is namespaced by user ID; it keeps at most 8,000 characters per message, while successful server sync restores the complete saved response. API Key material is memory-only.

## Explicit limitations / not yet implemented

- The Web Chat client exposes the newest 15 conversations, with at most 30 messages per conversation. User message text remains limited to 8,000 characters; assistant responses are persisted up to 32,000 characters and display an explicit truncation notice beyond that bound. A conversation JSON payload is limited to 5 MiB. The server list endpoint returns a bounded window of the newest 100 conversation rows (including deletion tombstones); server-side search returns up to 50 matches by default (maximum 100) and can query older saved conversations beyond the local recent window. Image bytes remain in the existing server FileStore; conversation history stores only validated file IDs and metadata.
- SQLite conversation rows are stored in a private 0600 database and scoped by authenticated user ID. Writes use optimistic revisions; simultaneous device updates are merged by stable message ID and retried, while deletions are represented by payload-free tombstones. This is persistence/synchronization, not end-to-end encryption or encrypted archival storage.
- The existing FileStore persists file bytes on disk without application-level encryption at rest. Server-side SQLite reference counts track each attachment across active conversations and devices; conversation tombstones release their references transactionally. File deletion returns a conflict while any saved conversation still references the file. Only uploads explicitly marked as Web Chat-originated are eligible for automatic cleanup after 90 days without references; general API uploads remain user-managed. This is not encrypted archival storage for highly sensitive images.
- Image attachments are tied to the API Key that uploaded them. A conversation containing images must continue using that same Key for subsequent multimodal requests; another Key may view the conversation but cannot submit it.
- Inline playback covers verified downloadable generated-file cards (MP3, WAV, M4A, OGG/Opus, FLAC, MP4 and WebM within the existing 12 MiB/file and 24 MiB/response budgets). The Web Chat composer now exposes a real-time Voice panel backed by the paired-extension Live Voice bridge: the browser requests microphone permission, resamples mono input to 16 kHz PCM16, streams binary frames over the one-time-token WebSocket, plays returned 24 kHz PCM16 frames in order, and displays final user transcripts and assistant text. The Voice session uses the selected managed API Key in memory and the existing ChatGPT Voice browser session; it is not a second text-generation request. The panel can optionally request camera permission and send JPEG snapshots into the same Voice session at up to one frame per second, waiting for each Worker confirmation before sending the next. Frames are uploaded as owner-scoped `vision` files, capped at 2 MiB each and 64 frames per session; restarting the camera preserves sequence/timestamp monotonicity. This is sampled frame input, not a continuous native WebRTC video track exposed by the Web Chat API, and it does not promise frame-accurate audio/video synchronization. Camera snapshots require the selected Key's `files` scope; Voice requires `audio` or `chat` scope. The bridge requires the signed-in ChatGPT browser session and paired Worker extension; pending microphone/camera permission prompts and asynchronous camera uploads are invalidated when the user stops the session or camera, so a late permission grant cannot restart capture. Browser transport/failure paths have automated tests, but real-device/browser-session acceptance is still required. Full media-component parity remains open.
- Bounded tool/function-call activity is displayed separately from assistant answer text (up to six events per assistant message; arguments/results are capped at 1,200 characters). Citation extraction accepts bounded `citations`, `content_references`, `search_result_groups`, `search_results`, `references`, `sources`, Responses-style `annotations`/`url_citation`, and explicit web-search/source-reference envelopes. Final assistant-message metadata is captured by the native Worker observer and attached to request-v6's single canonical terminal; the Broker validates and stores at most eight public-HTTPS references for Web Chat only. Valid UTF-16 annotation offsets are converted to the renderer's inert inline citation markers only when the native final-message text exactly matches the request-v6 terminal and media archival leaves that text unchanged; prompt-boundary rewrites, invalid or shifted ranges fall back to source cards. The browser revalidates links and renders text-only cards. PR #871 adds safe hover/focus previews for inline citations using the verified title, domain and bounded snippet; it does not render untrusted HTML. Web Chat persists standalone references on assistant messages, includes them in server conversation sync and merges them across devices without letting a newer text snapshot erase them. Copy and Markdown export replace private inline marker tokens with readable numbered citations and append the source list; JSON export preserves structured references. Full ChatGPT-native citation components, grouped cards and every citation layout remain open; the hover/focus preview slice is implemented but is not full citation parity. KaTeX 0.19.1 is bundled for TeX/Markdown math delimiters; native MathML is preserved through the allowlisted native renderer. This provides formula rendering and structural MathML support, but not every upstream ChatGPT math-card interaction or layout.
- The event journal and `Last-Event-ID` replay restore persisted delivery deltas across browser disconnects. They do not recreate a lost in-memory Broker generation after a server restart. If the Worker replays its durable terminal outbox, the server verifies the original request owner/Worker and uses the idempotent terminal finalization path for recoverable chat completions, including media archival and usage/quota reconciliation. Incomplete or unsupported replay evidence remains provisional/stalled and is never treated as a completed answer or charged twice.
- Super-admins can configure conversation-age retention from 0 (disabled) to 3650 days. Expired conversations are converted transactionally into payload-free deletion tombstones, and their attachment references are released. Tombstones are retained so long-offline devices cannot resurrect expired conversations; unreferenced attachment bytes continue to use the separate 90-day cleanup policy. This is conversation-level expiry, not an individual-message TTL. The server-side search and versioned JSON export/import API are also implemented.
- Queued Mode 1 requests can be cancelled before Worker selection. Once a Worker dispatch has completed, the existing Worker/Broker terminal path remains authoritative; the user-session API only sends the cancel signal and does not fabricate a Worker terminal.
- The UI does not create API Keys; users create and manage them in `/console#keys`.
- The Key is not persisted locally, but it is available to same-origin page JavaScript while the page is open; XSS prevention remains important.

## Real-time Voice usage

1. Open `/chat` in a secure browser context, choose a managed API Key with `chat` or `audio` scope, and make sure a paired Chrome Worker is online with its ChatGPT tab signed in.
2. Click **语音通话** and grant microphone permission. The panel connects to `POST /v1/audio/realtime/sessions` and the one-time-token `/v1/audio/realtime` WebSocket; it does not expose the long-lived API Key in the URL.
3. Speak naturally. The browser streams 16 kHz mono PCM16 input with a phase-preserving resampler and plays 24 kHz mono PCM16 output. User transcripts and assistant text are shown in the panel; the browser revalidates the user session every 60 seconds and releases the microphone/audio context when the session ends or the login expires.
4. To include visual context, click **开启摄像头** and grant camera permission. The client sends at most one JPEG snapshot per second, waits for `input_video.frame.sent` before advancing, and stops after 64 accepted frames. The selected API Key must also have `files` scope.
5. Click **结束语音** to finish the session and release microphone, camera, playback and WebSocket resources.

Final user speech transcripts and assistant response text are appended to the conversation selected when Voice starts and synchronized through the existing server conversation store; switching/deleting that conversation is blocked while the Voice session is active. If the user ends Voice mid-response or the upstream socket/track closes before `response.done`, the latest assistant DOM snapshot is sent as an interruption and saved with the `voice_partial` recovery status so it is not presented as a completed answer. A client-requested session finish waits for an explicit MAIN-world stop acknowledgement after the final interruption snapshot has been posted; if that acknowledgement is missing, the extension reports a stop error instead of claiming the Worker drained successfully. The browser waits up to eight seconds for the Broker's five-second drain deadline plus terminal-delivery margin. Raw audio is not archived, camera snapshots are not added to the ordinary conversation transcript, and a later Voice session does not yet hydrate prior text history into its live context. Camera support is a timestamped snapshot sequence, not continuous WebRTC video. Real Chrome/ChatGPT account, device permission, reverse-proxy WebSocket and long-duration stability acceptance remains an external gate.

## Security boundaries

- No third-party script, font, analytics or remote runtime is loaded.
- The page uses a same-origin CSP and does not render untrusted HTML.
- API Key plaintext is not stored in localStorage, sessionStorage, conversation history or exported Markdown.
- User session and Key ownership are enforced by existing server endpoints; the page is not an authorization boundary.
- The Mode 1 generation ingress requires both the HttpOnly user session and the selected managed API Key; it rejects master-key use and cross-account Key ownership.
- Native sidecar reads use the HttpOnly user session, resolve the request's API Key owner from Telemetry, conceal cross-user request IDs as 404, and are marked private/no-store with Cookie variation. The API Key itself is never returned by the native sidecar.
- FileStore persists a SHA-256 digest with each new file. Every read verifies both stored byte length and SHA-256 before returning bytes; legacy index rows without a digest are backfilled on first successful read. A mismatch fails closed as an I/O integrity error.
- Telemetry request history is stored as a private regular file (POSIX mode 0600), is read through the validated file descriptor, and rejects symlink/hard-link paths. Web Chat conversations and the SSE event journal protect their SQLite databases plus WAL/SHM/journal sidecars as private regular files (POSIX mode 0600). The local generated-media archive uses a private 0700 directory with a 0600 SQLite index, encrypted settings file, and 0600 object files; settings reads and atomic writes reject linked paths. These are filesystem access controls, not application-level encryption of conversation/telemetry data at rest.
- Image preview uses `GET /api/user/files/{file_id}/content`, which requires the HttpOnly user session, checks that the file's owner API Key belongs to the current account, and serves only `vision` PNG/JPEG/WebP/GIF bytes with `nosniff`, sandbox CSP, same-origin resource policy and `private, no-store` caching. Successful previews expose the verified digest as an ETag and `X-Chat2API-Content-SHA256` so byte identity can be checked without changing the standard FileObject JSON shape.
- `DELETE /api/user/files/{file_id}` applies the same account/owner/purpose/MIME checks, requires same-origin Origin/Fetch Metadata, and permits cleanup with the user session even if the uploading API Key has since been disabled.
- Image file IDs are validated before being restored from localStorage. The client never persists raw image bytes or API Key plaintext.
